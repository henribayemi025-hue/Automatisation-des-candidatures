# Audit de sécurité — Finjaro Accounting, 15/09/2026

Demandé par Beau : « cet outil tient la caisse, le stock, les factures et la
paie de vraies personnes ». Chaque point ci-dessous dit **ce qui a été tenté**,
**ce qui s'est passé** et **la preuve**. Classé par gravité réelle.

Rien n'a été corrigé en production. Les manœuvres offensives ont été jouées
dans une transaction annulée, et l'annulation a été vérifiée après coup.

État au moment de l'audit : 4 espaces de travail, 0 ligne de membre,
12 événements, 4 instantanés, 99 comptes dans `auth.users`.

## 1. GRAVE — un utilisateur peut entrer dans l'espace comptable d'un autre

### Ce que j'ai essayé

Simuler une utilisatrice réelle (`louceastrid9@gmail.com`, propriétaire de son
propre espace) et tenter d'atteindre l'espace de Beau, dont elle n'est pas
membre.

### Ce qui s'est passé

**Avant** — la base se comporte correctement :

```
membre_avant | evenements_lisibles_avant | espaces_visibles_avant
false        | 0                         | 1
```

**La manœuvre**, en trois instructions SQL ordinaires, à la portée de
n'importe qui possédant un compte :

```sql
-- 1. Je me crée une ligne de membre dans MON espace : autorisé, j'en suis propriétaire.
insert into finia_members(workspace_id, email, user_id, role, status)
values ('<mon espace>', 'louceastrid9@gmail.com', '<mon uid>', 'cashier', 'active');

-- 2. Je déplace ma propre ligne vers l'espace de quelqu'un d'autre.
update finia_members
   set workspace_id = '<espace de la victime>', role = 'owner'
 where lower(email) = lower('louceastrid9@gmail.com');
```

**Après** :

```
membre_apres | evenements_lisibles_apres | espaces_visibles_apres | mon_role
true         | 10                        | 2                      | owner
```

Dix événements comptables lus dans un espace qui ne lui appartient pas. Avec
`finia_is_member` vraie, elle peut aussi **écrire** des événements dedans :
inventer une vente, une dépense, une écriture.

### Pourquoi ça passe

La règle `finia_members_self_accept` ne vérifie qu'une chose :

```
UPDATE  using   lower(email) = lower(coalesce(auth.email(), ''))
        with check  lower(email) = lower(coalesce(auth.email(), ''))
```

Ni `workspace_id` ni `role` n'y figurent. En PostgreSQL, `USING` s'applique à
la ligne d'avant et `WITH CHECK` à la ligne d'après : tant que l'adresse reste
la mienne, je peux changer **tout le reste**, y compris l'espace auquel la
ligne se rattache.

Aucun garde-fou en dessous :

- aucun déclencheur sur `finia_members` ;
- `authenticated` détient le droit `UPDATE` sur **toutes** les colonnes,
  `role` et `workspace_id` compris.

### Ce qui limite la casse aujourd'hui

- `finia_members` est **vide** : personne n'a encore été invité, donc personne
  n'a de ligne à détourner. Mais l'écran Équipe sert exactement à en créer.
- Il faut connaître l'identifiant de l'espace visé. Ce sont des UUID, donc
  indevinables — mais ça ne protège que tant qu'aucun n'a fuité.
- `finia_is_owner` lit `finia_workspaces.owner_id`, **pas** le rôle : passer
  `role` à `owner` ne donne donc ni le droit de réécrire l'instantané ni celui
  de supprimer l'espace. C'est la lecture et l'écriture d'événements qui sont
  ouvertes, pas la propriété.

### CORRIGÉ le 15/09, avec l'accord de Beau

Migration `20260915131114_finia_members_guard_invitation`, additive, sans effet
sur la place de marché : `finia_members` est une table d'Accounting seule.
Versée au dépôt dans `supabase/migrations/`.

```sql
create or replace function public.finia_members_guard()
returns trigger language plpgsql security definer set search_path = public as $$
begin
  -- Le propriétaire gère les membres de son espace, sans restriction.
  if finia_is_owner(old.workspace_id) and finia_is_owner(new.workspace_id) then
    return new;
  end if;
  -- Accepter une invitation ne change que soi-même, jamais l'espace ni le rôle.
  if new.workspace_id is distinct from old.workspace_id
     or lower(new.email) is distinct from lower(old.email)
     or new.role is distinct from old.role then
    raise exception 'Accepter une invitation ne permet de changer ni l''espace ni le rôle';
  end if;
  return new;
end $$;

create trigger finia_members_guard
before update on public.finia_members
for each row execute function public.finia_members_guard();
```

### Vérifié après correction

La manœuvre rejouée à l'identique, dans une transaction annulée :

```
ERROR: Accepter une invitation ne permet pas de changer d'espace de travail
CONTEXT: PL/pgSQL function finia_members_guard() line 14
```

La variante réaliste — une caissière invitée qui se promeut — aussi :

```
ERROR: Accepter une invitation ne permet pas de changer de rôle
CONTEXT: PL/pgSQL function finia_members_guard() line 20
```

Les usages légitimes, eux, passent tous. Parcours complet rejoué :

| Étape | Qui | Résultat |
| --- | --- | --- |
| Inviter quelqu'un dans son espace | propriétaire | passe |
| Changer le rôle d'un membre (`cashier` → `manager`) | propriétaire | passe |
| Accepter l'invitation (statut, identifiant, nom affiché) | invitée | passe |
| Accès accordé après acceptation | invitée | `finia_is_member` vraie, 10 événements lisibles |

État de la base après tous ces essais, identique à avant : 0 membre,
4 espaces, 12 événements. Déclencheur en place.

L'écran Équipe peut maintenant être ouvert à de vrais utilisateurs.

## 2. GRAVE — sans compte, tout est perdu, et rien n'est récupérable

### Ce que j'ai vérifié

Où vivent réellement les chiffres, code et base à l'appui.

### Ce qui s'est passé

Deux régimes, très différents :

**Avec un compte.** Chaque action produit un événement poussé aussitôt dans
`finia_events` (`pushEvent`, `src/lib/collab.tsx`) ; en cas de coupure il
attend dans une file locale et part au retour du réseau. Le propriétaire écrit
périodiquement un instantané complet dans `finia_workspaces.data`. Le cache du
navigateur n'est qu'une copie : `saveCache` dit lui-même « le cloud reste la
source de vérité ». **Vider le cache, changer de téléphone, réinstaller : rien
n'est perdu**, `loadWorkspace` reconstruit depuis l'instantané et les
événements suivants.

**Sans compte — le mode local que l'application propose activement.** Tout
n'existe que dans `localStorage`, sous la clé `finia.cache.guest`. Mesuré sur
la démonstration : **552 578 octets**, 263 ventes, 576 écritures, 4 clients,
2 salariés. Rien de tout cela n'est ailleurs. Vider le cache, changer de
téléphone, désinstaller : **perte totale et définitive**. Aucune reconstruction
possible, il n'y a pas de journal d'événements côté serveur pour un invité.

C'est le cas que Beau redoutait : pour de l'argent, la perte vaut la fuite.

### CORRIGÉ le 15/09, avec l'accord de Beau

Rien à changer côté base. Trois mesures dans l'application.

1. **Dire la vérité à l'écran.** Au-delà de dix opérations enregistrées sans
   compte, un bandeau rouge annonce que les chiffres ne sont que sur cet
   appareil et qu'un changement de téléphone les efface, avec un raccourci vers
   la sauvegarde. Il ne s'affiche ni en démonstration ni pour deux essais, et se
   masque une fois lu.
2. **Sauvegarde dans un fichier**, depuis les réglages : `src/lib/backup.ts`
   écrit un fichier reconnaissable (`format`, `version`, date, résumé), passe
   par le partage du téléphone quand il existe — ce qui marche aussi dans la
   fenêtre de l'application Finjaro, où un téléchargement est parfois bloqué —
   et retombe sinon sur le téléchargement ordinaire.
3. **Rechargement**, avec une confirmation qui montre côte à côte ce que
   contient le fichier et ce qui va être remplacé. Un fichier étranger est
   refusé avec un message clair.

**Un trou trouvé pendant le test, et bouché.** Après un effacement complet,
l'application repart sur l'écran de connexion : les réglages sont
inatteignables, donc la restauration l'était aussi — exactement pour la
personne qui en a besoin, celle qui change de téléphone. Le rechargement est
donc proposé **sur l'écran de connexion** : « Vous changez d'appareil ?
Recharger une sauvegarde ».

**Le rechargement est un événement, pas un remplacement local.** Un simple
`replaceState` n'aurait rien envoyé en ligne et aurait disparu à la
reconstruction suivante. `workspace.restore` part en ligne comme une opération
ordinaire, les autres appareils convergent, et l'historique en garde la trace.

### Vérifié après correction

Cycle complet joué sur un appareil réellement vidé, page rechargée :

| Étape | Résultat |
| --- | --- |
| Démonstration chargée | 263 ventes, 576 écritures, 8 articles |
| Sauvegarde enregistrée | fichier `…-2026-09-15.finjaro.json`, 263 ventes dedans |
| `localStorage` vidé **et page rechargée** | 0 vente, l'application repart de zéro |
| Écran affiché | connexion, avec « Recharger une sauvegarde » |
| Sauvegarde rechargée depuis cet écran | 263 ventes, 576 écritures, nom retrouvé |
| Nouveau rechargement de la page | les chiffres tiennent |
| Fichier étranger déposé | refusé, message clair |

Aucune erreur JavaScript. Les huit scripts comptables restent verts.

## 3. IMPORTANT — le journal est inviolable, l'instantané ne l'est pas

### Ce que j'ai vérifié

Deux choses distinctes : le journal peut-il être réécrit, et ce que
l'application affiche vient-il bien du journal.

### Ce qui s'est passé

**Le journal est en ajout seul, et c'est solide.** `finia_events` n'a que deux
règles :

```
finia_events_select  SELECT  using  finia_is_member(workspace_id)
finia_events_insert  INSERT  with check  finia_is_member(workspace_id) AND actor_id = auth.uid()
```

Aucune règle `UPDATE`, aucune règle `DELETE`. Avec RLS active, une commande
sans règle est refusée : **un événement écrit ne peut être ni modifié ni
effacé**, même par le propriétaire. C'est exactement ce qu'on attend d'un
registre comptable.

Le moteur suit la même discipline : aucune suppression d'écriture dans
`src/lib/reducer.ts`, et l'extourne (`entry.reverse`) **ajoute** une
contre-passation au lieu d'effacer l'originale.

**Mais l'affichage ne vient pas que du journal.** `loadWorkspace` lit
l'instantané `finia_workspaces.data`, puis **seulement les événements dont la
`seq` dépasse `snapshot_seq`**. Or le propriétaire peut modifier ces deux
colonnes (`finia_owner_update`). En écrivant un instantané inventé et une
`snapshot_seq` élevée, il fait ignorer à l'application tout l'historique
antérieur.

Les preuves restent en base : les lignes de `finia_events` sont toujours là,
lisibles par un comptable ou un contrôleur. Mais **l'application, elle,
montrerait les chiffres réécrits**.

Un propriétaire qui maquille ses propres comptes reste son affaire. Ce qui
compte, c'est que personne ne prenne l'écran pour une preuve : la preuve, c'est
`finia_events`.

### Correction proposée — NON APPLIQUÉE

- Écrire noir sur blanc, dans la documentation du fiscaliste, que le registre
  opposable est `finia_events`, pas l'écran.
- Plus tard, si ça vaut le coût : horodater et chaîner les instantanés, ou
  refuser un instantané dont la `snapshot_seq` recule.

## 4. MOYEN — un téléphone perdu donne tout

### Ce que j'ai vérifié

Le contenu de `localStorage`, relevé clé par clé dans un vrai navigateur.

### Ce qui s'est passé

```
clé                        octets   contenu
finia.cache.guest          552578   {"company":{"name":"Démonstration — Boutique…
finia.theme                     6   system
finia.lang                      2   fr
finia.guest                     1   1
finia.demo                      1   1
```

Le cache contient en clair : noms et téléphones des clients
(`Restaurant Le Palmier`, `+237 6 55 10 20 30`), noms et salaires des
employés, 263 ventes, 576 écritures. Pour un compte connecté s'ajoute
`finia.auth`, qui contient le jeton d'accès **et le jeton de rafraîchissement**
de la session Supabase.

Quiconque ouvre le navigateur d'un téléphone déverrouillé lit tout cela, et
peut réutiliser la session.

C'est le fonctionnement normal d'une application web : `localStorage` n'est pas
chiffré, et il n'existe pas de coffre côté navigateur. Ce n'est donc pas un
défaut d'implémentation, mais c'est un risque à connaître et à réduire.

### Correction proposée — NON APPLIQUÉE

- Un verrou à l'ouverture (code à quatre chiffres) pour l'appareil partagé.
  C'est la mesure qui rapporte le plus pour le moins d'effort.
- « Se déconnecter » devrait aussi vider `finia.cache.*`, pas seulement la
  session.

## 6. SAIN, avec une réserve — membre retiré, et invitations

### Membre retiré

`finia_is_member` exige une ligne `status = 'active'`. Retirer la ligne, ou
passer le statut à autre chose, coupe **immédiatement** la lecture et
l'écriture en base, même sur une session déjà ouverte : le jeton reste valide,
mais toutes les règles retombent à faux.

En revanche, **ce qui est déjà dans son navigateur y reste** : le cache
`finia.cache.<espace>` garde la comptabilité telle qu'elle était au moment du
retrait. Il ne recevra plus rien, mais il gardera une copie. C'est la limite
d'une application qui fonctionne hors réseau, et il faut le savoir avant de
confier un accès.

### Invitations

On ne peut pas s'inviter chez autrui : l'insertion exige
`finia_is_owner(workspace_id)`. Et on ne peut accepter qu'une ligne portant sa
propre adresse, la comparaison étant insensible à la casse
(`lower(email) = lower(auth.email())`), ce qui est correct.

La réserve est le point 1 : la faille n'est pas dans le choix de la ligne, mais
dans ce qu'on a le droit d'y modifier une fois qu'on l'a.

## 7. À CONNAÎTRE — deux appareils hors réseau sur le même espace

### Ce qui se passe

Les deux files locales partent à la reconnexion. Le serveur attribue à chaque
événement une `seq` croissante, et `loadWorkspace` rejoue dans cet ordre. Comme
`applyEvent` est pure et déterministe, et que chaque événement porte son propre
identifiant, **les deux appareils convergent vers le même état**. Pas de
divergence, pas de doublon : l'identifiant est la clé primaire, un événement
déjà poussé est rejeté.

### La limite

La convergence est technique, pas comptable. **Aucun conflit métier n'est
détecté.** `applySale` fait `product.stock -= line.qty` sans plancher : si deux
appareils vendent hors réseau le dernier article, les deux ventes sont
enregistrées et le stock passe sous zéro.

Ce n'est pas silencieux : `runAuditChecks` signale le stock négatif dans
l'écran Audit. Mais c'est constaté après coup, jamais empêché.

## 8. Durcissement, sans urgence

`anon` et `authenticated` détiennent `DELETE, INSERT, REFERENCES, SELECT,
TRIGGER, TRUNCATE, UPDATE` sur les trois tables. C'est le réglage par défaut de
Supabase sur le schéma public.

Ce n'est pas exploitable aujourd'hui : l'API n'expose que lire, insérer,
modifier et supprimer, et chacune de ces quatre commandes est filtrée par RLS.
`TRUNCATE`, qui ignorerait RLS, n'est pas atteignable depuis le web.

Retirer les droits inutiles reste une bonne hygiène, à faire en même temps que
la correction du point 1 puisque les deux touchent les mêmes tables.
